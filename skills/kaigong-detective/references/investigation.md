# 从相似项目中产生问题和推荐

## 何时搜索

开工前的搜索门槛以 [SKILL.md](../SKILL.md#开工前强制搜索门槛) 为准：目标明确即搜；否则最多先一轮基本澄清，再进行真实发现—追查。即使需求简单、暂未发现外部事实缺口，也从已定流程的边界、失败状态或替代做法中选一项核验。用户明确只是测试时，保持测试模式，不将样例答案带入真实开发。

一次查询先围绕一个功能或取舍，避免堆很多品牌与词。找到候选后打开原文；信息已足以支持当前问题，就提出问题并等用户，不拖到整个调查结束；实施前仍须完成强制发现—追查链。不足或出现不同做法时，依据已有结果继续查更多同类项目。范围扩大时先复用已读资料，避免重新问已定偏好。

原版 Finding facts 的委派规则仍适用：可委派独立资料节点，未返回的依赖暂不解锁，其他问题正常进行。资料调查失败由主 Agent 接手已有记录，不声称已完成未执行的读取。

## 什么需求值得多轮调查

调查量由未决事实和决策代价决定，不由需求描述长短决定。简单工具仍须完成两次相关查询及原文问答；增加强约束、路线比较或时效要求后，在此基础上继续深入。

| 需求特征 | 适合继续查的事实 | 调查怎样推进 |
|---|---|---|
| 平台硬限制，如关闭页面后提醒、休眠恢复、跨设备同步 | 浏览器或系统官方能力、权限与限制，类似项目的实际实现 | 先查平台文档，再追查项目；发现约束冲突后提出是否换路线的问题 |
| 多条可行路线，如网页、扩展与桌面端 | 同场景的实现差异、部署与权限成本 | 找同一决策下的独立候选，读取原文，再按用户硬条件比较；不凑固定项目数 |
| 多项相互制约的条件，如离线、中文 OCR、大量 PDF、无独显、可商用 | 输入支持、资源需求、索引方式、关键依赖许可、维护状态 | 根据初查缺口逐轮追到源码、文档或 issue，查反例并保留未验证项 |
| 时效或证据冲突，如近期仍维护、免费额度、宣传与 issue 不一致 | 当前版本、发布日期、价格与条款、问题是否已修复 | 限定版本和时间，查原始发布者及独立证据，避免混用旧实现与新条款 |

例如“给自己做普通网页版番茄钟”可以只核对计时状态与刷新恢复，完成最小发现—追查，无须全面调研；但“关闭网页也要提醒、离线运行、跨设备同步、能强制屏蔽分心网站，比较网页/扩展/桌面三种路线”有多个可查的能力边界。技术事实先查证，是否接受安装、权限或功能退让再交给用户选择。

“高阶”须分清两层：多轮发现、追查、反证和排序是 Agent 的调查编排；`Mode`、`Site`、`Freshness` 等是服务接口参数。详见[元宝接口说明](yuanbao-api.md#已接入的业务参数)。不能把 `--tier deep` 说成打开了服务的深度模式，也不能把一次大查询包装成多轮调查。自带 CLI 已接入六项参数，使用前核对当前版本；真实版本未知时优先 Site。已知不支持或实际请求报参数错误时记录受限原因，不伪称已生效；当前接入与现场验证范围见接口说明。

向用户交付发现时，主动说出实际方式，例如“开工侦探经过元宝搜索的多轮搜索查到……”。如又做了反证核验或使用实际接入的站点、时效等参数，一并说清名称和得到的发现；不要让用户从来源数量猜测。标签根据当前问题的来源链判断，不根据整场调查的最高层级判断。参数功能只认真实请求记录，调查方式只认真实查询依赖。

## 高阶接口参数怎样选

至少有一项适用的语义参数进入真实请求；默认以 `Site` 从初查定位到的官方域名追查。不是把参数全部打开。调查编排与接口参数分别记录、分别报告。

| 当前事实缺口 | 请求选择 | 读取与核对 |
|---|---|---|
| 需要原始实现或官方限制，初查夹杂转载 | `--site 官方域名`；至多五个排除域名用 `exclude:a.com|b.com` | 逐项核对来源，Site 只作用于自然网页，VR 卡例外 |
| 近期发布、维护状态、过期说明或价格变化 | 按需求用 `--freshness d7` / `m3` / `y1` | 时间窗不是新旧版本证明；历史原文仍可另查 |
| 比较公开网页和优质垂直信源 | 标准/旗舰版再用 `--mode 0/1/2` | Mode 不是调查深度；极速版不支持 |
| 学术、技术新闻等相关垂域 | 版本支持时用 `--industry acad/news` 等 | gov/finance 只在技能允许的公开非个人范围；不因接口枚举扩大调查主题 |
| 关键内容在原文附件 | 确认旗舰版后用 `--deeplinks` | 返回子链仍需实际打开，不等于已读附件 |
| 当前候选召回不足 | 版本支持时用 `--cnt 20` 等 | Cnt 只增加服务端条数，单独使用不满足高阶语义参数门槛 |

每轮收到答案后重算事实缺口，已成功使用且仍适用的参数不为展示而重复调用。默认预算先按两次成功查询规划，追加调用包括失败尝试均受每轮预算约束。用户预算低于最低可完成量时，说明门槛尚未满足，不自动增加预算。

## 点餐原型回归样例

这是技能测试，不是真实开发授权。用户选择单店堂食、一人点餐、餐后结账、允许加菜后，下轮即搜索实际产品的订单边界：先发现相关产品，再用其官方域名追查加菜批次、已下单与购物车的区别或结账后限制。读取原文后用规定的搜索提问标签给出选择与推荐，等待回答；不能连续三轮纯偏好问题后宣布开始做网页。搜索结果仅支持某个产品时说明适配是建议，不把它扩大为行业统一规则。

## 项目怎么查

- 项目身份：原始仓库、上游/fork/镜像、版本或 commit。
- 做法：README、示例、相关代码、测试、功能限制。
- 取舍：ADR、design doc、issue/PR 里有无明确设计解释。
- 复用条件：维护、许可和关键依赖、输入输出、部署与成本。

不要只看 stars 排名。不要把官方营销等同实测，也不要把同作者多页或 PyPI/文档镜像当独立印证。搜索结果可能混入旧版，不能把旧实现与新许可拼成一个确定结论。网页请求成功也可能是挑战页，确认内容确为目标原文再收录为证据。

## 问题从哪里来

每个“开工侦探经过元宝搜索后提问”都要有能指明的触发发现：

- A 项目只支持某类输入：用户是否也接受这个边界？
- A/B 的路线不同：与用户目标相比，应优先哪一种？
- A 有付费依赖或已停止维护：用户是否接受这项成本/责任？
- A 的 README 宣传和实现有差异：用户是否愿意用具体样本先验收？
- 已有组件可以复用：用户是否还需要自研同一部分？

这是问题类型示意，不是具体项目事实。真正使用时，找不到来源就用“开工侦探提问”表达判断，不伪造搜索标记。事实已由资料查到时直接说明，不把“能查到的是什么”推给用户；问的是用户愿意怎样取舍。

作者明确解释取舍才标 `documented`；只见实际做法，可标 `inferred` 并把迁移建议写成自己的推断；无依据标 `unknown`。具体实现不能自动证明作者是因为性能、成本或用户需求这样设计。推荐复用模式也要检查用户当前约束是否适用，不说“别人这样做，所以你也必须这样”。

## 问题和推荐分别溯源

普通问题：`❓ Q1 · 开工侦探提问`。搜索产生的问题：`🔎 Q2 · 开工侦探经过元宝搜索后提问`。搜索问题至少展示一个触发事实、来源和原文位置，推荐单独展示依据、适配理由、风险或待验证项。

普通问题的推荐可以是模型的设计判断；若把事实包装成外部依据，就必须有真实检索与原文。搜索问题的推荐也可以保留未知，但需说清本轮查到的依据不足以选择，不虚构一个确定答案。回答“是”仍接受当前推荐，其余偏好由用户决定。

## 多轮比较与优先级

将同一功能的候选放在同一 `comparison_group`；端到端转换器与单纯生成库等互补层分组。先列用户硬条件，逐项标支持、冲突或未知。有明确硬冲突的不能进入推荐序列；硬条件未知的只能标条件性候选。

组内排序依据：需求匹配、证据质量、维护、复用成本、许可边界。每项写判断和出处，没资料写未知。比较的是“当前任务先试哪个”，不是全网通用质量排名。用户成本优先时可以改变默认顺序，但不能覆盖硬性约束。

输出示意：

| 优先级 | 项目 | 实际做法/可复用点 | 为什么排这里 | 来源与未知 |
|---|---|---|---|---|
| P1（条件性） | A | 原文实际记录的做法 | 更贴近用户已定条件，仍需样本验证 | 原文链接；缺什么 |
| P2（条件性） | B | 另一种实际做法 | 优点和额外代价 | 原文链接；缺什么 |
| 排除 | C | 明确与硬条件冲突 | 具体冲突 | 反证原文 |

多个候选都不满足时明确没有可推荐方案，不硬选P1。若资料不足，不为凑P2/P3编新候选。未知不默认等同“差”，应说明它为什么限制当前推荐，哪些补查或样本会改变排序。

## 搜索升级与停止

direct/multi/deep 只用于记录实际搜索动作。默认一次先找，再按缺口升级：找更多相似项目、比他们的做法、读解释，再查反例或独立来源。开工前至少完成两次不同 RequestId 且有真实依赖的查询，不要求默认三份报告或全部参数。找到可支撑当前问题的资料就向用户提问，后续决定依赖用户回答时停止下探。

预算包括失败请求；默认每轮最多18次，不自动购买或定时执行。一次查询的RequestId不能复用成“多轮”。账号/额度错误停止重复请求，临时网络错误至多重试一次。无法查到或读到的项保留未知，不能声称不存在。
